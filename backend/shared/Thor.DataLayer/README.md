# Thor.DataLayer

Shared EF Core data-access package for Thor. It owns:

- **Data models** — EF Core entities live under `Models/` and are mapped via
  `TenantDbContext` (per-tenant DB) or `MasterDbContext` (Master metadata DB).
- **Migrations** — schema changes are managed with EF Core migrations
  (`Migrations/`, generated by the `dotnet ef` CLI).
- **Repositories** — generic CRUD access (`Repositories/IRepository.cs`,
  `Repositories/Repository.cs`) that entity-specific repositories build on.
- **Tenant database connections** — `Data/TenantDbContextFactory.cs` builds a
  `TenantDbContext` from a `TenantConnectionInfo` (host, port, database,
  username, password), or from an already-open connection.

## What this package deliberately does *not* do

Thor is database-per-tenant on a shared Aurora PostgreSQL cluster (see
`docs/architecture/ADR.md` §6). This package is **tenant-agnostic**: it does
not resolve *which* tenant to connect to, and does not talk to Secrets
Manager. Callers are responsible for resolving a tenant's connection
parameters (via the tenant routing table and Secrets Manager — see
`Thor.DataConnectionManager`) and passing a fully-formed `TenantConnectionInfo`
(or an already-open connection) in. This keeps the boundary clean — tenant
resolution/routing logic belongs to the caller, not to the data layer.

```csharp
var connectionInfo = new TenantConnectionInfo(
    Host: resolvedTenant.ClusterEndpoint,
    Database: resolvedTenant.DatabaseName,
    Username: resolvedTenant.DbUser,
    Password: resolvedSecret.Password);

using var db = new TenantDbContextFactory().Create(connectionInfo);
```

## Consuming this package

This is a **project**, consumed via `<ProjectReference>` — not packaged or
published anywhere. Every consumer lives in this same repo (`Thor.Api`,
`Thor.TaskApi`, `Thor.DataConnectionManager`, etc.), so there's no packaging
step: build the consuming project and you get the current source directly.

```xml
<ItemGroup>
  <ProjectReference Include="..\..\shared\Thor.DataLayer\Thor.DataLayer.csproj" />
</ItemGroup>
```

(adjust the relative path to wherever the consuming project sits under `backend/`).

## Adding a model and generating a migration

1. Add the entity class under `Models/`.
2. Add a `DbSet<TEntity>` property to `Data/TenantDbContext.cs` (per-tenant DB)
   or `Data/MasterDbContext.cs` (Master metadata DB).
3. Generate a migration using the matching design-time factory
   (`Data/TenantDbContextDesignTimeFactory.cs` or
   `Data/MasterDbContextDesignTimeFactory.cs`), which needs a real (or local)
   Postgres connection string at migration-generation time (not an actual
   reachable server — `migrations add` builds the model in memory and never
   opens the connection):

   ```sh
   export THOR_DATALAYER_HOST=localhost
   export THOR_DATALAYER_DATABASE=thor_datalayer_design
   export THOR_DATALAYER_USER=postgres
   export THOR_DATALAYER_PASSWORD=postgres
   dotnet ef migrations add <MigrationName> --project backend/shared/Thor.DataLayer --context TenantDbContext --output-dir Migrations/Tenant
   ```

   Use the `THOR_MASTERDB_*` env vars and `--context MasterDbContext
   --output-dir Migrations/Master` for Master DB migrations instead. Because
   this project now has two `DbContext` types, `--context` is required on
   every `dotnet ef` invocation — omitting it is ambiguous.

   If the env vars are unset, both design-time factories fall back to
   `localhost:5432` with a `postgres`/`postgres` login — convenient for local
   dev, but only for `migrations add` (schema diffing), not for `database
   update` against a real database.

For schema changes specifically: add the EF Core migration, done — there's no
version bump or repack step anymore. Rolling a new Master DB schema out is a
normal migration; rolling tenant DB schema changes out across the tenant
fleet follows the Blue/Green deployment strategy described in
`docs/architecture/ADR.md` §6.4.
